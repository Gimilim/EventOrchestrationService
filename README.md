# EventOrchestrationService

Данный проект реализует API для работы с событиями.
Используется актуальная версия .net (10) на момент реализации проекта

Архитектура приложения:

Приложения разбито на отдельные проекты для соответствия Clean Architecture + разбито на микросервисы

Подключенные технологии:
-Используется fluentValidation
-Подключены Moq и xUnit для тестов
-Для интеграционных тестов используется Testcontainers.PostgreSql (Обязательно нужен докер для прогона интеграционных
тестов!)
-Есть планы на переход на OpenApi вместо сваггера
-PostgreSQL для хранения данных
-Юнит тесты крутятся на InMemory SQLite
-Интеграционные на 17 версии Постгре
-Реализована оптимистическая блокировка для исключения многих сценариев одновременной перезаписи сущностей
-Подключен мониторинг

Общая информация:
-Каждый микросервис разделен на 6 проектов: юнит тесты, интеграционные тесты, апи слой, доменный слой, инфраструктурный
слой и апликейшин слой:
Domain - Ядро бизнес-логики
Application - Use Cases, содержат в себе ДТО модели, интерфейсы, реализацию сервисов
Infrastructure - Реализация внешних зависимостей: работа с бд (миграции, конфигурации), работа с данными (реализации
репозиториев), фоновый обработчик броней
API - Точка входа
Монолитная версия проекта перенесена в папку legacy

-Реализован глобальный перехватчик ошибок для всех исключений
-Реализована пагинация для запроса всех событий (или других сущностей)
-Методы базово покрыты тестами (включая методы сервисов и методы репозиториев)
-Добавлена фоновая обработка
-При первом запуске будет создана БД через миграцию.
-Реализован паттерн репозиторий для разделения ответственности
-Реализована автоматическая накатка всех непримененных миграций при запуске проекта
-Реализована базовая ролевая модель (user и admin). (Интуитивно понятные ограничения, пользователь способен отменить
только свое бронирование, админ любое и т.д.)
-Реализована выдача JWT токена, секрет написан в конфигурации (исключительно в рамках тестового проекта). Для продакшена
стоит вынести в другое место.
-Подключена Кафка для обмена сообщений между сервисами
-Реализован паттерн Инбокс и Аутбокс
-Реализовано кеширование двух запросов: получение события по ИД и получение топ 10 событий.
-Кеширование топ 10 событий выполняется на сутки, событие по ИД по умолчанию т.е. 5 минут
-Есть возможность задать значение по умолчанию через аппсетингс
-При изменении событий кэш всегда будет сброшен для данного события (включая сценарии, где бронируем новые места)
-Для топ 10 событий кэш не сбрасываем никогда. Считаем, что актуальные события закреплены на сутки и не будут сильно
колебаться от бронирований и других событий (включая их удаления, осознанный выбор, считается, что популярное событие
уже точно не будет удалено)

События:
События содержат поля TotalSeats и AvailableSeats, которые отвечают за набор мест на событии и количество мест, которые
в данный момент доступны для бронирования.
AvailableSeats - автовычисляемый, не может быть больше общего количества мест (так же предусмотрен сценарий, который не
позволит изменить общее количество мест,
которые будут противоречить занятым )

Общая концепция:
-Возможность создавать, редактировать, удалять, обновлять события, а так же делать бронирование (с фоновой обработкой)
на эти события.
Фоновая обработка перехватывает все бронирования из БД в статуте ожидания и обрабатывает их. На текущий момент заглушка,
имитирующая долгую деятельность

- ### Фондовая обработка бронирований

`BookingBackgroundService` — фоновая служба, которая обрабатывает бронирования. После созданяи бронирования, если
событие небыло обработано - будет повтоно обработано фоновым сервисом

**Как работает:**

- Каждые 5 секунд сервис запрашивает из БД все бронирования со статусом `Pending`, которые висят в этом статусе более 5
  минут
- Если обработка была произведена 3 раза -- помечаем такое бронирование, как неудачное (отдельный статус Failed)
- В штатном режиме событие будет опубликовано в кафку для дальнейшей обработки со стороны event сервиса (для проверок с
  той стороны на возможность бронирования), только после ответа от сервиса событий - будет изменен статус

**Аутентификация и получение JWT-токена**

Для доступа к защищенным эндпоинтам API требуется JWT-токен. Токен можно получить через Swagger UI.

### Шаг 1. Запустите приложение

Убедитесь, что проект запущен. Swagger UI будет доступен по адресу:  
`https://localhost:5001/swagger/index.html` (порт может отличаться).

### Шаг 2. Зарегистрируйте пользователя

В Swagger найдите эндпоинт `POST /auth/register`. Нажмите `Try it out` и отправьте запрос с телом:

```json
{
  "login": "your_login",
  "password": "your_password",
  "role": 1
  // 1 = User, 2 = Admin (опционально, по умолчанию 1)
}
```

### Шаг 3. Войдите в систему

Найдите эндпоинт POST /auth/login. Отправьте запрос с телом:

json
{
"login": "your_login",
"password": "your_password"
}

В ответе вы получите JWT-токен (обычно в виде строки или в поле token).

### Шаг 4. Авторизуйтесь в Swagger

Скопируйте полученный токен. Нажмите на кнопку Authorize (в правом верхнем углу Swagger UI). В поле Value введите:

Bearer <ваш_токен>

Нажмите Authorize. Теперь все защищенные эндпоинты (помеченные замком) будут доступны для тестирования.



- ### Мониторинг, трассировка и логирование (OpenTelemetry & Serilog)

В проектах слоя **API** каждого из трех микросервисов (booking-service, events-service, users-service)
развернута полноценная система сквозного мониторинга, распределенной трассировки и структурированного логирования на
базе стандарта **OpenTelemetry (v1.18.0)** и **Serilog**.

### Что было сделано:

1. **Развернута инфраструктура мониторинга**:
   В docker-compose.yml добавлен единый инфраструктурный стек в общей Docker-сети event-orchestration-network:

* **Prometheus** (v2.51.0) — для сбора и хранения метрик.
* **Jaeger** (v1.56) — для сбора и визуализации распределенных трассировок (gRPC OTLP).
* **Grafana** (v10.4.2) — для построения аналитических дашбордов.

2. **Внедрен OpenTelemetry SDK в .NET 10**:

* Настроена автоматическая инструментация входящих HTTP-запросов (AspNetCore), исходящих запросов через HttpClient и
  запросов к базам данных (EntityFrameworkCore).
* Реализован **гибридный сценарий запуска**: инфраструктура работает в контейнерах, а сервисы — локально. Связь
  контейнеров с хост-машиной настроена через шлюз host.docker.internal.
* Конфигурация конечной точки OTLP вынесена в переменные окружения (Otlp__Endpoint: http://localhost:4317) в файлах
  launchSettings.json.

3. **Реализован сбор метрик через Prometheus (Критическое требование)**:

* В каждом сервисе активирован скрапинг-эндпоинт app.MapPrometheusScrapingEndpoint().
* Метрики успешно отдаются в текстовом формате по адресу http://localhost:<порт_сервиса>/metrics.
* Настроен файл prometheus.yml для автоматического опроса всех трех локальных сервисов. Все таргеты имеют статус UP в
  панели *Status -> Targets*.

4. **Интегрировано структурированное логирование (Критическое требование)**:

* В качестве основного провайдера логирования подключен **Serilog**.
* Настроен вывод логов в консоль в стандартизированном JSON-формате с помощью CompactJsonFormatter для последующей
  бесшовной интеграции с системами сбора логов (например, ELK / Fluentd / Loki).

5. **Создан дашборд Grafana**:

* В репозиторий добавлен JSON-файл конфигурации дашборда Grafana.
* Настроены графики для отображения трех обязательных метрик производительности ASP.NET Core:
* http_server_request_duration_seconds (Распределение времени обработки запросов / Latency).
* http_server_active_requests (Количество одновременно обрабатываемых запросов / Concurrent requests).
* http_server_request_duration_seconds_count (Общее количество запросов для подсчета пропускной способности /
  Throughput).
